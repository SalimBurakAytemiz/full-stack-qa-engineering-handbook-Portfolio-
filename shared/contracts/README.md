# Shared Contracts (Section 27)

Real, enforced contracts — not just an index pointing at code, and not
decorative placeholders. Each contract is enforced by a real test that
fails the suite (`npm test --workspace backend`) on drift.

| Contract | Canonical definition | Drift check |
|---|---|---|
| REST response shapes | `shared/schemas/{auth,common,health,notifications,orders,products}/*.schema.json` | AJV, wired into `QA-DEMO-SYSTEM/api-tests` (see `evidence.api-tests.newman-ajv-suite`) |
| GraphQL schema | `graphql/schema.graphql` (generated snapshot of `QA-DEMO-SYSTEM/backend/src/graphql/schema.js`) | `QA-DEMO-SYSTEM/backend/tests/graphql-contract-drift.test.js` |
| WebSocket notification push message | `websocket/notification-push-message.schema.json` | `QA-DEMO-SYSTEM/backend/tests/realtime-contract-drift.test.js` |
| `order.paid` domain event payload | `events/order-paid.schema.json` | `QA-DEMO-SYSTEM/backend/tests/realtime-contract-drift.test.js` |

## How the GraphQL drift check works

`graphql/schema.graphql` is a committed snapshot generated by
`QA-DEMO-SYSTEM/backend/scripts/print-graphql-schema.js`, which calls
`graphql`'s own `printSchema()` on the real, running schema object — it
is never hand-edited. `graphql-contract-drift.test.js` re-runs
`printSchema()` at test time and does a byte-for-byte comparison against
the committed snapshot. Any schema change — intentional or accidental —
fails this test until the snapshot is regenerated and the diff is
reviewed and committed. This is the standard "schema snapshot testing"
pattern, not new machinery invented for this repository.

## How the WebSocket/event drift check works

Two JSON Schemas describe the two real message shapes this backend
actually emits: the `/ws` push message, and the `order.paid` event
payload persisted in the `events` table. `realtime-contract-drift.test.js`
drives the real flow (login → create an order → receive the real push
message; separately, read the real persisted event row from the test
DB) and validates both against their schemas with AJV. This is
different from `websocket.test.js`, which only asserts a couple of
functional fields (message text, `type`) — the drift test validates the
*entire* shape, so an unnoticed field type change or an unexpected new
field fails it even when the functional test still passes.

## Why REST has standalone JSON Schema files and GraphQL doesn't

GraphQL's SDL is already a formal, machine-enforced contract (the
execution engine itself rejects a query that doesn't match it); adding
a second, redundant JSON Schema layer on top would duplicate the same
fact in two places, which the registry's "one fact, one owner" rule
avoids. The snapshot-diff approach above gives GraphQL drift detection
without that duplication.

## Regenerating the GraphQL snapshot after an intentional schema change

```
cd QA-DEMO-SYSTEM/backend
node scripts/print-graphql-schema.js
git diff shared/contracts/graphql/schema.graphql   # review before committing
```

## Verified to actually catch drift

Both drift checks were deliberately broken and confirmed to fail before
being trusted: a fabricated `type Fabricated` block was appended to the
GraphQL snapshot (test failed, reverted cleanly), and the WebSocket
schema's `is_read` field was changed to an impossible `const: 999` (the
WebSocket test failed while the unrelated event-payload test in the same
file still passed, confirming the checks are independent — reverted
cleanly). See `.ai/DECISIONS.md`.
